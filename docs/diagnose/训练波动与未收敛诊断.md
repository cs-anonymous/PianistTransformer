# 训练损失、验证指标与测试 PN/PP 的关系

## 结论修正

此前把 60 epoch 后 probe loss 仍有小幅下降解释为“主要问题是没有收敛”，这个判断不适合作为当前研究主线。训练 loss 在正常训练中继续下降是预期现象；小幅震动也不等于训练失败。

当前真正要回答的是三个关系：

1. training loss 降低时，validation PN/PP 是否改善；
2. validation PN/PP 是否能够预测 test PN/PP；
3. 如果 loss 继续降低而 validation PN/PP 变差，原因是过拟合还是训练目标与 PN/PP 不一致。

60 epoch 矩阵没有记录 validation PN/PP，因此不能回答这三个问题。它只记录了 validation NLL、train probe NLL 和辅助项，不能据此判断 PN/PP 是否收敛。

## 应采用的方向

当前 PN/PP 使用 Wasserstein 距离，数值越低越好。若论文希望使用“指标越高越好”的方向，应定义一个单调变换，例如：

$$
Q=\frac{1}{1+HR},
$$

其中 $HR$ 是与人类参考距离归一化后的 PN/PP 距离。训练 loss 越低、$Q$ 越高才是同一方向的比较。分析原始 HR 时必须明确“越低越好”，否则会把趋势方向读反。

对每个 checkpoint，应同时记录：

$$
(L_{train},L_{valid},HR_{valid},HR_{test}).
$$

判别逻辑是：

| 观察到的趋势 | 应解释为 |
|---|---|
| $L_{train}$ 降低，$L_{valid}$ 降低，$HR_{valid}$ 降低 | 正常学习，目标和指标暂时一致 |
| $L_{train}$ 降低，$L_{valid}$ 升高，$HR_{valid}$ 升高 | 传统过拟合的证据 |
| $L_{train}$ 和 $L_{valid}$ 都降低，但 $HR_{valid}$ 升高 | 训练目标与 PN/PP 不一致，不能称为普通过拟合 |
| $HR_{valid}$ 改善，但 $HR_{test}$ 变差 | validation 与 test 分布、采样协议或估计方差不匹配 |

因此，后续不能只根据 training loss 或 validation NLL 选择 checkpoint。

## 已有数据说明了什么

### 先看顺序链路：相邻变量之间是否传递一致

五个变量不是拿来做无差别的两两相关，而是按训练与评估流程形成一条链：

$$
L_{train}\rightarrow L_{valid}\rightarrow HR_{valid,TF}\rightarrow HR_{test,TF}\rightarrow HR_{test,sampled}.
$$

下图逐 epoch 展示标准化趋势和每一条相邻边的散点相关。所有指标均按“越低越好”定义；正相关表示相邻变量随 checkpoint 同向变化，并不代表它们数值方向相同或训练目标已经一致。

![五个变量的相邻链路诊断](../results/baseline0807_epoch_hr_20260807_170343/five_metric_adjacent_diagnostics.png)

旧的 epoch 1--12 sweep 只有一条训练轨迹，不能代表跨 seed 的稳定性。现在将最新的 60 epoch、多 seed validation TF 诊断接入第一条边；其余涉及 test AR 的边仍使用旧实验中严格配对的 12 个 checkpoint。表中同时给出样本数和数据来源，避免把不同实验的相关性当成同一条完整轨迹。

| 相邻链路 | Pearson | Spearman | n / 数据来源 | 诊断 |
|---|---:|---:|---|---|
| train loss → valid loss | 0.978 | 0.991 | 12，baseline0807 | 很强；训练目标能传到验证 NLL |
| valid loss → valid TF HR3（PN/PP composite） | **0.921** | **0.955** | **42，6 runs × 7 checkpoints** | 最新多 seed 结果显示 loss 能稳定排序 TF HR；PN-only 为 `0.905/0.966`，PP-only 为 `0.923/0.953` |
| valid TF HR → test TF HR | 0.966 | 0.965 | 12，baseline0807 | 很强；固定 teacher-forcing 指标在 validation/test 间一致 |
| test TF HR → generated-MIDI test HR | **0.840** | **0.783** | 12，同一 test-score 子集 | 中等偏强；从解析 TF 指标到采样 rollout 指标时仍有额外偏差 |

这次更新改变了第一条边的判断：在固定 68-work、`rollout_k=0` 的同一 validation 协议下，6 条训练轨迹的 loss 与 PN/PP TF HR 同向变化，第一条链路目前不再是主要问题。60 epoch run 尚未通过 plateau gate，所以这里是强诊断证据，不是已收敛模型的正式 loss 优劣结论。

末端 **test TF HR → generated-MIDI test HR** 现在是主要问题。将两者限制在相同的 12 个 test score 后，Pearson / Spearman 为 `0.840/0.783`；若把 generated-MIDI HR 扩展到原始 19-score aggregate，则为 `0.795/0.755`。因此 score 集合差异会贡献一部分偏差，但同一 score 子集仍存在 rollout、采样和 MIDI materialization gap。

## 端到端相关性

端到端只定义为完整链条的首尾关系：

```text
train loss → generated-MIDI test AR HR
```

目前只有 baseline0807 的 12 个 checkpoint 同时具备这两个量，因此端到端相关性只能在这 12 个点上计算，不能把 60 epoch 的 validation-only 结果硬接到旧 test 结果上。

| 端到端关系 | Pearson | Spearman | Kendall | 口径 |
|---|---:|---:|---:|---|
| train loss → test AR HR | **0.270** | **0.580** | **0.424** | 12 checkpoints，同一 12-score 子集 |
| train loss → test AR HR | 0.183 | 0.573 | 0.394 | 12 checkpoints，原始 19-score aggregate |

这个端到端结果较弱，但不能据此说四条相邻边都弱。前三条相邻边仍然很强，主要断点是最后的 `test TF HR → test AR HR`；端到端首尾相关较弱，是这个断点累积后的结果。

旧的 12-point 表仍有两个限制：epoch 12 没有新的 Trainer eval event，且 test AR 每个 checkpoint 只有一次生成评估。仅用精确 eval 的 epoch 1--11 时，旧链路的 `valid loss → valid TF HR` 为 `0.630/0.864`，`test TF HR → test AR HR` 为 `0.793/0.700`；这些数字用于历史对照，不能覆盖最新 60 epoch validation 证据。

这组相邻诊断采用新补齐的固定全量 validation TF HR（68 个 valid works，$k=0$）、固定 12 个 test works 的 test TF HR，以及两种 generated-MIDI test HR 汇总。它与下文早期的 $m=32,k=8$ validation rollout HR 不是同一种评估协议；两者结果不同不能直接视为互相矛盾。旧结果只描述其当时的抽样 rollout 估计，以下新图和表才用于判断当前五变量的顺序链路。

在这份旧协议的数据里，NLL 从 19.9891 降到 16.4200，但 validation HR 没有单调下降，且 epoch 5 和 10 明显变差。对这 12 个点，validation NLL 与 validation HR 的 Pearson 相关约为 $0.045$，Spearman 相关约为 $-0.378$。新补齐的全量 TF 评估显示相邻 valid loss → valid TF HR 的秩相关明显更高；差别很可能与 rollout/TF 评估协议及 $m=32$ 抽样估计有关，需要通过同协议重算和跨 seed 复现来确定，不能把旧的低相关直接推广到当前链路。

这组数据不能单独证明过拟合，因为 validation NLL 也在下降。它更直接支持“逐 note teacher-forcing NLL 与 rollout PN/PP 的目标不一致”，同时也提示 validation HR 估计本身需要控制随机性。

### 2. validation 与 test 的数值变化相似，但 checkpoint 排名仍不够可靠

同一 sweep 中，validation HR 与 test HR 的 Pearson 相关约为 $0.966$，但 Spearman 相关只有约 $0.406$。这说明两者的大幅异常点会同时出现，但不能据此认为 validation 可以稳定地给 checkpoint 排序。

例如 epoch 7、9、11 的 test HR 分别为 $1.7725$、$1.6958$、$1.7401$；validation HR 分别为 $3.0072$、$3.0326$、$3.0608$。validation 不能可靠区分这些相近 checkpoint 的优劣。

更关键的是，当前 test HR 每个 epoch 只有一次完整测试推理，不能把一个点当作无噪声真值。test 只能用于最终一次或少量预注册 checkpoint 的确认，不能反过来参与 checkpoint 选择。

### 3. 不同属性已经出现明确的目标冲突

同一训练轨迹的原始 test 距离显示：

- PN IOI 从 epoch 1 的 $37.18$ 降到 epoch 12 的 $34.99$；
- PP IOI 从 $17.48$ 降到 $11.61$；
- PN velocity 从 $15.84$ 升到 $19.08$；
- PP velocity 从 $7.92$ 升到 $9.37$。

所以“总体 HR”即使短期改善，也可能是 IOI、duration 的改善掩盖了 velocity 的恶化。这正是属性干扰，不能用一个总 loss 或一个总 HR 代替分析。

### 4. 当前 validation 与 test 的采样协议并不完全相同

`src/evaluate/eval_inr_window_rollout_hr.py` 使用 `sampling_strategy=sample`，但 `--seed` 主要用于选择 validation work/window；评估函数没有对每个 checkpoint、score 和 rollout 重新设置与 test 相同的稳定采样 seed。

而 `src/inference/infer_inr_testset.py` 会为每个 score 构造稳定 seed，并在每个 sample task 中设置 Python、CPU 和 CUDA RNG。因此 validation 和 test 的随机估计过程并不严格相同。即使两者使用同一个 HR 公式，checkpoint 间的差异也可能包含采样协议差异。

这必须先修正，再讨论 validation 是否代理 test。

## 正确的下一轮实验

### 第一步：建立 validation PN/PP 曲线

对每个训练 checkpoint 运行同一个 validation rollout evaluator，至少记录 epoch 1--12 或 4、8、12、24、36、48、60：

- 固定 validation score/window 清单，并将清单写入 manifest；
- 固定 rollout $k$、$m$、属性归一化和 pooling；
- 使用与 test 完全相同的 sampling strategy；
- 使用每个 score 固定且可复现的 sampling seed；
- 每个 checkpoint 用至少 3 个 sampling seeds，报告均值和标准误；
- 分别报告 PN/PP 的 IOI、duration、velocity、pedal，另外报告预注册的 composite HR。

validation evaluator 应支持一个明确的 deterministic mode。若正式 test 使用 sampling，就不能只用 validation mean/greedy 结果替代它；mean/greedy 只能作为额外诊断。

### 第二步：直接计算代理能力

在不使用 test 选择 checkpoint 的前提下，用固定 validation 曲线回答：

1. $L_{train}$、$L_{valid}$ 与每个 validation 属性的 Pearson/Spearman 相关；
2. validation composite 对 test composite 的 rank correlation；
3. validation 选择的 checkpoint 与 test 最优 checkpoint 的 rank regret；
4. 不同 training seed 下这些相关性的置信区间。

如果 $L_{valid}$ 降低而 $HR_{valid}$ 升高，说明应优先修改 loss 或训练方式。如果 $HR_{valid}$ 能排序但 $HR_{test}$ 不能，说明应优先扩大 validation representative set、固定采样协议或增加 validation sampling repeats。本轮最新结果属于后一种：valid TF HR 的排序已经稳定，剩余问题集中在 TF 到 sampled MIDI 的 rollout gap。

### 第三步：区分过拟合和目标不一致

每个 checkpoint 必须同时看训练和 validation 的 NLL：

- 训练 NLL 下降、validation NLL 上升、validation HR 上升：过拟合；
- 训练 NLL 下降、validation NLL 下降、validation HR 上升：NLL 与 rollout PN/PP 不一致；
- NLL 和 validation HR 都改善，但某个属性恶化：多属性 loss 权重或输出分布发生竞争；
- validation HR 稳定、test HR 波动：测试样本量或采样方差问题。

在这四种情况分离前，不应继续用“延长 epoch”作为主要修复方案。

## 是否加入 1/2-step rollout loss

可以尝试，但不应直接把当前的 `rollout_eval_weight` 当成训练 loss 权重。`src/train/train_inr.py` 的 `_rollout_eval_loss_for_k` 在 `torch.no_grad()` 下计算，它只会把 rollout loss 写入 validation `eval_loss`，用于诊断或 checkpoint 选择，不会产生训练梯度。

如果要让模型真正学习 free-running 条件，应保留 teacher-forcing loss 作为锚点，并在训练 batch 中加入 detached feedback 的第二次前向：

```text
L_train = L_TF + lambda_rollout * L_rollout(k)
```

其中 `L_rollout(k)` 的输入反馈来自模型前一次输出，但反馈本身 detach；梯度通过第二次前向的 logits 回传。建议顺序是：

1. 先做 `k=1`，`lambda_rollout` 取 `0.10` 和 `0.25`；
2. 只有 k=1 在同一 test score 集合上改善 AR HR，且不损害 valid TF HR，才尝试 `k=2`；
3. 不建议第一步直接用 `lambda=0.5` 或完全替换 `L_TF`，这样可能破坏当前已经稳定的 valid loss → valid TF HR 链路；
4. 每个候选条件至少使用 3 个 training seeds，并固定 sampling seeds，分别报告 PN/PP TF HR、PN/PP AR HR、生成长度和失败率。

仓库已经有 `dagger_prefix_training` 和 `k1_twopass` prefix cache 路径。它通过让训练看到预测前缀来缓解 exposure bias，通常比直接把长 rollout 反向传播到 k=2 更稳定，建议作为第一版 rollout-aware 训练基线。完整 k=2 rollout loss 应作为后续对照，而不是一开始替换现有 NLL。

这项实验的成功标准不是 rollout loss 数值变小，而是同一 test score 集合上的：`test TF HR → test AR HR` 相关性提高、AR HR 的均值下降，同时 valid TF HR 不出现系统性恶化。test 只能在协议冻结后的预注册 checkpoint 上做确认，不能用来选择 `lambda_rollout`。

## 对训练方案的修正建议

当前优先级应调整为：

1. 保留现有 loss 作为 TF 锚点，并固定 validation PN/PP checkpoint metric；
2. 优先用 DAgger/predicted-prefix 训练做 k=1 exposure-bias 基线；
3. 再比较真正的 `L_TF + lambda_rollout * L_rollout(k)`，先 k=1，再 k=2；
4. 按属性观察 TF 与 AR 的变化，尤其是 velocity、IOI 和反馈长度；
5. 只有 rollout-aware 训练在多 seed 上稳定改善 AR HR 后，才考虑替换或扩大 rollout 项的权重。

现阶段可以把第一条链路视为基本成立；需要解决的是 **test TF HR → test AR HR** 的 rollout gap。60 epoch 训练仍未通过 plateau gate，因此新的 rollout-aware 条件也必须沿用相同的收敛判定和多 seed 设计。
