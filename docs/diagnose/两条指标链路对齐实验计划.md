# 两条指标链路对齐实验计划

## 目标

当前先解决两个相邻但不同的问题：

```text
valid loss  ->  valid teacher-forcing HR
test teacher-forcing HR  ->  test autoregressive HR
```

这两个问题不能同时用一个新 loss 解决。第一条链路是“训练目标是否能反映同一条件分布下的质量指标”，第二条链路是“teacher forcing 条件分布能否在模型自反馈下保持稳定”。应先完成第一条，再固定训练目标和 checkpoint 规则，处理第二条。

本文所说的 validation subset 暂按仓库现有 fixed validation subset 理解：68 个 eligible ASAP works，每个 work 使用固定 valid window，并且每个 work 至少有两条 performance。仓库中没有发现名为 `1y` 的独立 manifest；如果 `1y` 指另一份清单，应将其替换为该清单，但必须固定 score/window manifest 后再比较。

## 当前证据

在 `results/baseline0807_epoch_hr_20260807_170343/` 的 1--12 epoch checkpoint 上，现有 `valid_tf_full.json` 已经同时记录了：

- `tf_loss`：同一 grouped validation evaluator 中的 teacher-forcing loss；
- PN/PP 的 IOI、duration、velocity、pedal Wasserstein；
- PN/PP 论文 HR。

原始 baseline0807 的 1--12 epoch 结果曾给出：

| 相关关系 | Pearson | Spearman |
| --- | ---: | ---: |
| Trainer `valid_loss` -> valid TF HR | 0.670 | 0.893 |
| evaluator `tf_loss` -> valid TF HR | 0.669 | 0.888 |
| Trainer `valid_loss` -> valid TF HR | 0.658 | 0.893 |

随后对 baseline/cached 两种条件、3 个 seeds、7 个 checkpoint（4/8/12/24/36/48/60）重新做了固定 68-work、`rollout_k=0` 的 TF 诊断，共 42 个 checkpoint。Trainer `valid_loss` 与 composite HR 的 Pearson/Spearman 为 `0.921/0.955`；PN-only 为 `0.905/0.966`，PP-only 为 `0.923/0.953`。详细结果见 [`第一条链路_60epoch_PN_PP_TF诊断.md`](第一条链路_60epoch_PN_PP_TF诊断.md)。

因此第一条链路目前不再是主要疑点。原始 epoch 5 仍然是局部异常，但它没有在 6 条长训练轨迹中持续出现。当前需要集中处理的是 `test TF HR -> test autoregressive HR` 的 rollout gap。

端到端只定义为 `train loss -> generated-MIDI test AR HR`。旧 baseline 12-point 配对结果在相同 12-score 子集上的 Pearson/Spearman 为 `0.270/0.580`（原始 19-score aggregate 为 `0.183/0.573`）。这不是四条相邻边的替代品：相邻表中前三条仍然较强，主要断点是 `test TF HR -> test AR HR`，其 Pearson/Spearman 为 `0.840/0.783`。60 epoch 训练目前只有 validation TF 结果，尚未生成对应 test AR 结果，因此不能把两批数据拼成一个虚假的端到端相关性。

## 第一阶段：固定 subset，建立逐作品诊断

### 1. 冻结评估协议

固定以下内容，并将其写入一个 manifest：

- validation works 和每个 work 的 window 起止位置；
- score source、GT performance 列表和排序；
- checkpoint 列表；
- `rollout_k=0`，即 teacher-forcing 解析输出；
- materialization strategy、timing support、pedal mask 和所有 normalizer；
- evaluator commit、config hash、sidecar/data manifest hash。

epoch 12 不能直接使用旧 Trainer `eval_loss`，因为该点沿用了较早的 validation event。所有 checkpoint 必须重新触发一次完整 validation，或者只分析具有精确对应 eval event 的 epoch。

### 2. 同一批数据同时记录三类量

每个 checkpoint、每个 work、每个 feature 都记录：

```text
pointwise NLL / BCE
grouped teacher-forcing loss
PN/PP raw W1 和 human-relative HR
```

至少拆分为：

- IOI；
- duration；
- velocity；
- pedal；
- PN；
- PP；
- 论文 HR（四属性，PN 与 PP 分开）。

同时记录有效 note 数、GT performance 数、zero-score-IOI note 数、mask 数和失败/缺失数。

### 3. 统一聚合口径

当前 Trainer loss 主要按 batch/example/note 聚合，而 TF HR 按 grouped performance 和 work 聚合。必须同时输出三种聚合：

1. note-weighted：保持现有 Trainer 口径；
2. performance-weighted：每条 performance 等权；
3. work-weighted：每个 work 等权，作为与 fixed validation HR 最接近的口径。

先不改变模型，只检查哪一种 loss 聚合与 TF HR 的 checkpoint 排名最一致。若只是 work weighting 能显著提高相关性，问题是聚合定义，不是分布族。

### 4. 查明 epoch 5 异常

对 epoch 5 与相邻 epoch 4/6 做 score-level 对照，列出每个 work 的：

- loss 增量；
- PN/PP IOI、duration、velocity、pedal 增量；
- 生成/解析失败；
- valid window 长度；
- GT performance 数量；
- zero-score-IOI 和 tail target 比例；
- 每个属性的有效 mask 比例。

如果异常集中在少数 works，应单独审计数据、alignment 和窗口；如果所有 works 的某一个属性同时异常，再检查该 head、support、normalizer 或 checkpoint 保存/加载。

## 第二阶段：定义“逼近 TF HR”的判据

loss 不需要在数值上等于 HR。二者单位和含义不同，合理目标是：

- checkpoint 排名一致；
- work-level 误差排序一致；
- 不同属性的改善方向一致；
- 对异常 checkpoint 有相近的识别能力。

每个候选 loss 都报告：

- Pearson：检查线性关系；
- Spearman/Kendall：检查 checkpoint 排名；
- top-1/top-3 checkpoint overlap；
- rank regret：loss 选择的 checkpoint 与 TF HR 最优 checkpoint 的差距；
- 每个属性独立的相关性；
- 4-fold work-level split 的均值和区间。

不能在同一个 validation subset 上反复选择 loss 权重并把最优结果当作泛化证据。建议把 68 works 按 work 固定分成 4 folds：三 folds 用于诊断/选择，剩下一 fold 用于确认，并轮换四次。test 只能在协议冻结后做一次确认。

## 第三阶段：逐步引入更贴近 HR 的 loss

按以下顺序比较，每次只改变一个因素。

### A. 现有 NLL/BCE baseline

记录各属性的 pointwise loss、grouped loss 和 HR。它是所有比较的参照。

### B. 同一 grouped evaluator 的 TF metric surrogate

仓库已有 `_pn_pp_metric_w1_loss`，它从 teacher-forced logits 构造四个属性的预测分布，并与 grouped GT 计算与论文 HR 一致的诊断距离；pedal 使用相应的 grouped mean difference。

第一步只把它作为 **validation diagnostic** 计算，不改变训练。确认它与 valid TF HR 的逐 work 数值和排名一致后，才考虑加入训练。

必须核查：

- prediction/GT 的 bin 和 support 是否完全一致；
- zero-score-IOI 的 support 是否一致；
- PN 是逐 note 对齐还是 group pooled；
- PP 是否按 work pooling；
- normalizer 是否与最终 HR 相同；
- group/work 权重是否相同。

### C. 单属性辅助 loss

若 B 与 TF HR 对齐，再逐个加入：

```text
NLL + lambda_ioi * TF-PN/PP-CDF-W1(IOI)
NLL + lambda_duration * TF-PN/PP-CDF-W1(duration)
NLL + lambda_velocity * TF-PN/PP-CDF-W1(velocity)
NLL + lambda_pedal * TF-PN/PP-distance(pedal)
```

先只加一个属性，避免四个目标的竞争掩盖原因。每个 lambda 必须在 validation development folds 中预注册，并在 held-out fold 上确认。

### D. 四属性组合

只有在单属性结果明确后，才比较四属性组合。组合项应采用与最终 HR 相同的 feature normalizer 和 work-level weighting。若组合 loss 的总值改善，但某个属性恶化，必须保留属性级结果，不能只报告一个平均数。

## 第二条链路：test TF HR -> test AR HR

第一条链路稳定后，冻结 loss、checkpoint 选择规则和 sampling protocol，再分析第二条。

### 1. 使用同一 test score 集合

TF 和 AR 必须使用相同的 score list、相同的 GT subset、相同的窗口和相同的 HR 定义。不能把 12-score test TF 与 19-score generated MIDI test 混在一条相关性中。

### 2. 逐步增加 free-running 程度

固定 checkpoint 和 sampling seeds，比较：

```text
k=0: teacher forcing
k=1
k=2
k=4
k=8
k=16
full-score AR
```

每个阶段分别记录四个属性的 PN/PP HR、生成长度、反馈值偏差和失败率。目标不是马上让 full AR 等于 TF，而是定位偏差从哪个 rollout 长度开始出现，以及哪个属性首先失稳。

### 3. 诊断 decoder feedback drift

对每一步比较：

- GT feedback 与 sampled feedback 的 raw timing/velocity/pedal 差异；
- 下一步 logits 的 NLL 和 distribution distance；
- 累积 prefix length 与 HR 的关系。

如果 k=1 就明显变差，优先检查 decoder feedback representation 和 materialization；如果 k=4 以后才变差，优先考虑 prefix training/DAgger 或 scheduled sampling；如果只在长窗口边界恶化，优先检查 continuation 和 window merge。

## 当前决策规则

- 先做同一 subset、同一 checkpoint 的逐作品诊断，不马上改模型。
- 先解决聚合、mask、support、normalizer 和异常 checkpoint，再判断 loss 是否需要改。
- 第一条链路只要求 loss 能稳定排序 TF HR，不能要求两个数值相等。
- 第一条链路已有多 seed 诊断支持，下一步进入 TF -> AR 的 rollout drift 诊断。
- 不要把 `rollout_eval_weight` 误认为训练 loss 权重；当前实现只在 `no_grad` validation 中组合 rollout loss，不会更新模型参数。
- 若训练 rollout-aware 目标，先保留 `L_TF`，比较 `L_TF + 0.10 L_rollout(k=1)` 和 `L_TF + 0.25 L_rollout(k=1)`，再考虑 k=2；同时把 `dagger_prefix_training` 作为较稳定的 predicted-prefix 基线。
- 任何新的 loss 必须同时报告四个属性、PN/PP、training seed 和 sampling seed 方差。
- 如果新的 loss 只改善 velocity 而损害 timing 或 pedal，视为 trade-off，不视为总体解决。

## 最小下一步

先实现一个只读诊断输出：

```text
valid_tf_alignment/
  manifest.json
  checkpoint_rows.csv
  work_rows.jsonl
  feature_rows.jsonl
  correlations.json
  epoch5_outlier_report.json
```

其中 `checkpoint_rows.csv` 记录 checkpoint-level loss/HR，`work_rows.jsonl` 记录每个 work 的贡献，`feature_rows.jsonl` 记录属性级 loss/HR。完成这一步后，才能判断下一步是修聚合、修异常样本、加 CDF-W1 surrogate，还是处理真正的目标错位。


## 20 epoch rollout-loss matched run（当前诊断）

为避免用三个 checkpoint 过度解释相关性，已完成 `baseline`、`rollout10`（`L_TF + 0.10 L_rollout(k=1)`）和 `rollout25`（`L_TF + 0.25 L_rollout(k=1)`）三种条件的 20 epoch 训练。三种条件均为 seed 11、10 个 train works、每 work 3 条 performance、2 个 windows，并在 epoch 4/8/12/16/20 保存 checkpoint。

TF 和 AR 使用同一个三 score list、同一个 seed 11 和同一 sampling protocol。TF 诊断在每个 score 的固定窗口上计算，AR 评估在同一 score list 的完整生成 MIDI 上计算；因此下面的 TF→AR 结果是同 score list 的小规模诊断，严格的窗口级一一对应仍需后续补齐。

| 条件 | loss→TF HR Pearson/Spearman | TF HR→AR HR Pearson/Spearman | loss→AR HR Pearson/Spearman |
|---|---:|---:|---:|
| baseline | 0.281 / 0.800 | 0.981 / 0.700 | 0.139 / 0.500 |
| rollout10 | 0.250 / 0.600 | 0.996 / 1.000 | 0.191 / 0.600 |
| rollout25 | 0.185 / 0.600 | 0.999 / 1.000 | 0.155 / 0.600 |

结果显示，rollout loss 没有把训练 loss 与最终 AR HR 的相关性提高到可靠水平；三种条件的 loss→AR Pearson 仍只有 0.14–0.19。TF HR 与 AR HR 在这个三 score、五 checkpoint的小样本中高度同向，但这不能抵消训练 loss→AR 的弱相关，也不能据此宣称 full test 已解决。进一步把可用的每个训练 checkpoint（epoch 4、8、9–20，共 14 个点）都做了 TF 评估后，loss→TF HR 的 Pearson/Spearman 为 baseline `0.487/0.798`、rollout10 `0.478/0.679`、rollout25 `0.417/0.578`，仍没有显示 rollout loss 带来改善。epoch 12 在三种条件中都出现共同的 HR 恶化，说明当前主要问题仍包括 checkpoint/训练轨迹异常或数据评估对齐，而不是单纯的 teacher-forcing 与 AR 反馈差距。

绝对 HR 数值只用于辅助查看误差大小，不能作为 rollout loss 是否有效的主判据；不同 rollout 权重的训练总 loss 也不应跨条件直接比较，因为目标函数本身已经改变。完整明细见 `results/rollout_loss_corr_seed11_20ep_v1/correlations_20ep.json`。

## 10-score test 子集补充结果

考虑到 3-score pilot 过小，固定了 10 个 test works（19 个 test works 中有 12 个满足至少两条 ASAP performance 的条件，因此抽取 10 个），列表见 `results/rollout_loss_corr_seed11_20ep_v1/metrics/test_subset_m10_scores.txt`。三种条件均完成 epoch 4/12/20 的 full-score AR，TF 则完成 epoch 4/8/12/16/20。

10-score 的三点 AR 结果为：

| 条件 | TF HR→AR HR Pearson/Spearman | train loss→AR HR Pearson/Spearman |
|---|---:|---:|
| baseline | 0.935 / 1.000 | 0.351 / 0.500 |
| rollout10 | 0.961 / 1.000 | 0.382 / 0.500 |
| rollout25 | 0.973 / 1.000 | 0.367 / 0.500 |

由于 AR 只有 epoch 4/12/20 三个点，Spearman=1 只能说明这三个点排序一致，不能视为稳定相关性证据。Pearson 也只有三点，仍属于端点诊断。rollout loss 尚未显示出可靠改善；rollout10 的 loss→AR Pearson 从 baseline 的 0.351 上升到 0.382，但证据强度不足以支持结论。

因此停止继续扩展 10-score AR 的剩余 epoch。下一步若要画“不同 seed 的五变量完整链路曲线”，必须为至少两个额外 seed 重跑同一 10-score score list、同一 checkpoint 网格和同一 AR 协议；当前 rollout matched run 只有 seed 11，不能把不同协议或不同 score 子集拼成多 seed 曲线。

### 关于 epoch loss 曲线的口径更正

此前图中的 epoch loss 取的是该 epoch 最后一个 optimizer step 的 batch loss。20 epoch 实验每个 epoch 有 6 个 optimizer steps，因此这个点不能代表整轮训练集的平均 loss。重新对每个 epoch 的 6 个 step 求平均后，baseline、rollout10、rollout25 的 epoch-mean training loss 都是整体单调下降的；epoch-12 的明显异常主要仍出现在 HR 评估，而不是完整 epoch 的训练平均 loss。

因此，训练数据每轮是否完整遍历并没有矛盾：每轮确实遍历全部 training data，之前的图只是使用了最后一个 batch 的 loss。修正后的曲线见 `results/rollout_loss_corr_seed11_20ep_v1/m10_seed11_curves_corrected.png`。

## 当前训练 window 覆盖核查

20 epoch rollout run 的生成配置实际设置了 `block_notes=512`、`overlap_ratio=0.125`、`max_windows_per_work=2`。因此每个 work 的原始 windows 先按 12.5% overlap 生成，再在 `PianoCoReNodeSFTDataset` 中截断为前两个 windows。当前 10 个 training works 的实际 dataset 长度为 42 个 examples；取消 `max_windows_per_work` 后为 54 个 examples，约有 22.2% 的 window-performance examples 被截掉。

按 note 覆盖计算，当前截断后的总体覆盖率约为 86.2%。受影响的长作品包括：Italian Concerto（1084 notes，覆盖 88.6%）、BWV 857 Fugue（1318 notes，覆盖 72.8%）和 BWV 860 Fugue（1751 notes，覆盖 54.8%）。因此确实存在部分作品只训练到前半段或前部窗口的问题，但不是所有作品都只训练了一半。

在取消截断前，不应单独把 overlap 改为 50%。如果保持 `max_windows_per_work=2`，50% overlap 的前两个 windows 只覆盖 `[0,768)`，反而可能比当前 12.5% overlap 的前两个 windows 覆盖更少。正确的对照顺序应是先保持 overlap=0.125、取消 window cap，确认完整覆盖的影响；再单独比较 50% overlap。

## 50% overlap、24 epoch 的 CINR 对照（2026-10-27）

本轮实验已按上述更严格的覆盖方案完成：`block_notes=512`、`overlap_ratio=0.5`、取消 `max_windows_per_work`；每个 work 的 valid window 在曲首或曲尾二选一，并从 train 中排除与 valid 区间有任何交集的窗口。新的 split 审计得到 152 个 train works、139 个 valid works、1,532 个 train windows 和 139 个 valid windows，train/valid window 交集为 0。

三条 CINR 条件均训练 24 epoch，每个 epoch 结束后验证，并保存 `epoch-4/8/12/16/20`：

| 条件 | 配置 | epoch 1 valid loss | epoch 24 valid loss | best-checkpoint composite HR | PN HR | PP HR |
|---|---|---:|---:|---:|---:|---:|
| CINR slot-sum | `extra__rep_slot_sum` | 19.950 | 15.521 | 2.583 | 1.746 | 3.420 |
| CINR canonical | `cinr__default_dlm_k1_bounded5` | 20.886 | 15.532 | 2.767 | 1.800 | 3.735 |
| CINR canonical + rollout | canonical + `0.10 L_rollout(k=1)` | 20.810 | 15.610 | 2.582 | 1.712 | 3.451 |

这里的 HR 仍是论文已有的四属性 Wass 比例算术平均，数值越低越好；三组 inference 都是同一 19-score、3 samples 协议。rollout 条件的 HR 略优于两条无 rollout 条件，但幅度很小，不能仅凭这一轮宣称 rollout 已解决 test TF→test AR 链路。

验证 loss 的完整序列是逐整数 epoch 记录的。slot-sum 在 epoch 7、9、12--13 等处有小幅回升，canonical 在 epoch 8、12、14 等处有小幅回升，rollout 在 epoch 2--4 和 9/11 处波动更明显；三组从中期以后总体下降，24 epoch 没有出现持续性 valid loss 上升。训练 loss 的最后 batch 仍有 batch-level 抖动，不能代替 epoch mean；应以 `trainer_state.json` 的整轮统计或后续聚合脚本为准。

按每轮 156 个 optimizer step 的 epoch mean 汇总，普通两组的总训练 loss 为：slot-sum `19.876 → 16.637 → 15.845 → 15.677 → 15.465 → 15.333 → 15.276`（epoch 1/4/8/12/16/20/24），canonical 为 `19.968 → 16.948 → 16.088 → 15.744 → 15.557 → 15.398 → 15.296`，均为整体下降。rollout 条件应分开看目标函数：TF 部分为 `19.927 → 16.598 → 16.165 → 15.756 → 15.551 → 15.387 → 15.324`，rollout k=1 部分为 `19.930 → 17.183 → 16.924 → 16.538 → 16.310 → 16.085 → 15.985`；包含 `0.10 L_rollout` 的总 loss 为 `21.890 → 18.289 → 17.832 → 17.385 → 17.157 → 16.970 → 16.897`。因此三组的训练目标在 epoch mean 层面都下降，rollout 总 loss 不能与普通条件的 TF loss 直接横向比较。

本轮曾发现旧调度器按 manifest 估计样本数设置 `eval_steps`，而 sidecar 过滤后的实际 dataloader 更短，导致验证点落在 `1.04、2.08、...`。最终实验已启用 `force_epoch_eval`，修正为真正的 epoch hook；旧偏移运行不纳入结论。结果目录为 `results/cinr_overlap50_24ep_20261026_200500/`，split summary 为 `data/train_valid_asap3_nonasap05_edge50_v1_summary.json`。
